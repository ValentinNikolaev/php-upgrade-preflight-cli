# PHP Upgrade Preflight v0.3.0

Released 2026-08-18.

## Purpose

v0.3.0 turns the final-target preflight into a bounded, evidence-backed staged analysis while keeping the analyzed project read-only. It retains the PHP `^8.0` runtime floor and ships the same Core, CLI, and Laravel package set.

## Highlights

- Schema `0.8` adds required `staged_resolution`, target-platform-profile projections, Composer execution provenance, adjacent stage attempts, selected candidate-state fingerprints, blocker lifecycle history, and stage-scoped source impact, risk, effort, tests, and actions.
- Rooted `laravel/framework` projects can run sequential Composer evidence across every contiguous adjacent path from Laravel 7 through 13. Direct final-target resolution, framework guidance, and staged resolution remain independent conclusions.
- Schema `1.0` target-platform profiles support honest `partial` and closed-world `complete` semantics. Complete profiles require Composer 2.2 or newer and model unlisted safely simulated platform packages as absent.
- Compatible Composer mode retains the configured host environment for projects that need private repositories. Restricted mode uses analyzer-owned Composer configuration, scrubs controlled credential and proxy sources, and requests best-effort offline behavior. Restricted mode is not an OS network sandbox.
- The optional `FrameworkStageTargetProvider` lets an adapter contribute deterministic staged targets without changing the required v0.2 interfaces. Old-style adapter source can migrate after testing and widening its Core constraint to permit v0.3.
- Core no longer inspects another framework's application skeleton. Laravel provider, kernel, facade, configuration, and test-double inspection moved into the Laravel adapter behind the new optional `SourceUsageVisitorProvider` extension point, and each collector now traverses the parsed syntax tree in isolation.
- The Markdown projection reports fields the schema did not record as absent instead of substituting defaults, and every Composer diagnostic carries a required `outcome` so a timeout, a missing Composer binary, and a genuine non-zero exit are distinguishable.

## Install

The commands below require the signed v0.3.0 tags and Packagist packages to be published and verified; see [Release integrity](#release-integrity). Use a separate tools directory when the target runs PHP 7 or must remain byte-for-byte unchanged:

```bash
mkdir php-upgrade-tools
cd php-upgrade-tools
composer require php-upgrade-preflight/cli:^0.3 php-upgrade-preflight/laravel:^0.3
```

Project-local installation is available to compatible PHP 8 projects:

```bash
composer require --dev php-upgrade-preflight/cli:^0.3 php-upgrade-preflight/laravel:^0.3
```

v0.3 is a normal Composer-package release. It does not ship a PHAR or a versioned runtime container; the repository Docker files remain development tooling.

## Complete-profile staged quick start

Create `/work/profiles/php-8.3-production.json` from authoritative target-environment inventory. A complete profile is a claim that every safely simulated supported platform package not listed is absent:

```json
{
  "schema_version": "1.0",
  "completeness": "complete",
  "packages": {
    "php": "8.3.0",
    "ext-curl": "8.3.0",
    "ext-mbstring": "8.3.0",
    "ext-xdebug": false,
    "lib-curl": "8.6.0",
    "php-64bit": "8.3.0"
  }
}
```

Then run the externally installed analyzer in restricted mode and place the report outside the target:

```bash
vendor/bin/upgrade-intel analyze \
  --path=/work/legacy-app \
  --from-php=8.1 \
  --target=laravel/framework:^13.0 \
  --target-platform-profile=/work/profiles/php-8.3-production.json \
  --framework=laravel \
  --composer-mode=restricted \
  --format=json \
  --output=/work/upgrade-reports/legacy-app.json
```

Read `resolution.status`, `transition.framework_guidance[].status`, and `staged_resolution.execution_state` plus `staged_resolution.status` separately. A skipped staged analysis or restricted offline metadata miss is uncertainty, not proof of dependency incompatibility. Later-stage source findings inspect the original source snapshot; the analyzer does not pretend earlier recommended source edits were applied.

## Migrating from v0.2

1. Change package constraints from `^0.2` to `^0.3`; Composer does not consider different `0.MINOR` lines compatible automatically.
2. Dispatch report parsing on `metadata.schema_version`. Keep schema `0.7` handling unchanged and add a separate schema `0.8` path.
3. In schema `0.8`, accept required `staged_resolution`, `composer_execution`, a required `outcome` on every Composer diagnostic, nullable `request_summary.target_platform_profile`, and nullable `platform.profile`.
4. Preserve direct-final `resolution`, `transition.package_changes`, and top-level `source_impact`. They are not replaced by staged fields.
5. Check `staged_resolution.execution_state` before its independent status, retain the ordered blocker registry, and validate the selected predecessor/input/output fingerprint chain before advancing between stages.
6. Resolve stage source-impact references through the staged source-impact registry and stop recommendations at the first blocked, unknown, skipped, or missing stage.
7. Adapter authors may keep unchanged implementations of the required interfaces, but must test against v0.3 and publish a Composer constraint that permits Core `^0.3`. Implement the optional stage-target provider only when the adapter can supply exact, ordered, evidence-backed targets.
8. A project analyzed without an active Laravel integration no longer receives `service_provider`, `facade_alias`, `middleware_reference`, `console_command`, `config_reference`, `test_double`, or `deprecated_queue_dispatch` source usages. Laravel analysis is unchanged; adapters that want framework-shaped source inspection implement `SourceUsageVisitorProvider`.

The full consumer migration is in [Schema and compatibility](../schema.md#migrating-from-07-to-08); adapter migration is in [Framework adapters](../adapters.md#migrating-an-old-style-adapter).

## Source-breaking internal API changes

These affect code that constructs Core classes directly. The public `UpgradeAnalyzer::analyzeUpgrade()` operation, the CLI and Artisan surfaces, and the required adapter interfaces are unchanged.

- `PhpUpgradePreflight\Core\Source\ContextualSourceUsageVisitor` was removed. Its behavior lives in `PhpUpgradePreflight\Laravel\Source\LaravelSourceUsageVisitor` and reaches the scanner through `SourceUsageVisitorProvider`.
- `ReportFileWriter::__construct` takes a `ReportDestinationFilesystem` port instead of a `Symfony\Component\Filesystem\Filesystem`, and `ReportAssembler::assemble()` now requires actionable source impact as an earlier argument.
- `PackageRef`, `UpgradeTarget`, `EffortEstimate`, and the severity, confidence, blocker-type, and solver-relation vocabularies validate their input at construction and throw `InvalidArgumentException` on values that could not appear in a canonical report. Reading a malformed lockfile is unaffected: unusable entries are skipped and reported as uncertainty.
- The generic CLI and the Artisan command render `--format` through one shared `ReportWriter` contract and format resolver in Core.

A framework adapter that throws while contributing source collectors or compatibility rules, a Composer package with a malformed `extra.php-upgrade-preflight` manifest, and a rule returning an out-of-vocabulary severity are now contained: the offending adapter or rule is skipped and named as evidence-backed uncertainty instead of ending the run without a report.

## Compatibility and limits

- Analyzer packages support PHP 8.0 through PHP 8.x. Laravel's own requirements determine higher floors for project-local adapter installation; normal and lowest-dependency consumers cover Laravel 8–13.
- Complete-profile reproducibility covers the modeled platform decision only. Repository metadata, downloads, credentials, the selected Composer executable, helper processes, and OS network isolation remain separate inputs.
- Candidate-state fingerprints identify manifest and lock content, so the state chain is comparable across hosts and checkout directories. The raw `candidate_lock.sha256` and `candidate_lock.content_hash` evidence stays local to the workspace Composer wrote it in.
- Composer scripts, plugins, installation side effects, interaction, and progress are disabled for analysis scenarios. The target manifest, lock, vendor tree, and source remain unchanged; all simulated edits occur in analyzer-owned temporary workspaces.
- Composer success does not prove application runtime compatibility or deployment readiness. Every result is decision-support evidence and must be followed by application tests and deployment validation.

## Release integrity

Publication requires matching verified signed `v0.3.0` tags in the monorepo and all three distribution repositories, checksum-bound archives, dependency inventory and provenance, Linux and Windows consumer audits, Packagist reference verification, and a published-package rerun of the complete-profile staged quick start with byte-for-byte target immutability.

Release evidence — workflow run, approved commit, signed-tag verification, distribution split commits, archive and inventory checksums, immutable-fixture checksum, release URL, and Packagist references — is recorded in this file when publication completes.
