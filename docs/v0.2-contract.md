# v0.2 report and transition contract

This is the normative human-readable contract for the v0.2 release line. Its machine-checked counterpart is [`tests/fixtures/contracts/v0.2.json`](../tests/fixtures/contracts/v0.2.json). Laravel's approved hop catalog remains in [`laravel-v0.2-transition-matrix.json`](../tests/fixtures/contracts/laravel-v0.2-transition-matrix.json).

## Transition support

Transition support measures framework guidance coverage. It does not measure whether Composer can resolve the requested final target.

- `supported`: source and target each resolve to one major, and either an approved direct rule pack covers the request or every required adjacent hop has an implemented rule pack.
- `partially_supported`: source and target each resolve to one major, and a contiguous implemented prefix from the source covers at least one but not every required adjacent hop. Covered prefix hops may emit guidance; every gap is listed as uncertainty, and guidance stops at the first gap.
- `unsupported`: no safe guidance path exists. This includes ambiguous or unknown majors, no implemented required hops, same-major or downgrade requests, and catalog boundaries.

An ambiguous source or target produces `unsupported`, an empty hop list, and an uncertainty explaining the observations. The analyzer must not select the lowest, highest, locked, or rooted major as a best guess when the evidence conflicts. A missing hop is explicit: a nonempty contiguous covered prefix from the source makes the overall status `partially_supported`; a missing first hop makes it `unsupported`, even if isolated rule packs exist after the gap. Post-gap coverage is ignored because guidance may not cross the gap.

The retained Laravel 7 to 9 direct pack is a supported direct path. Adjacent composition is preferred when every hop exists, but the direct pack remains independently regression-tested.

## Independent report dimensions

`resolution.status` is the result of isolated Composer scenarios for the requested final target. `transition.framework_guidance[].status` is the rule-pack coverage assessment. Every combination is meaningful: for example, Composer can be `feasible_with_changes` while framework guidance is `partially_supported`, or Composer can be `blocked` while framework guidance is `supported`.

`transition.package_changes` belongs only to the selected successful final-target Composer scenario. A framework hop is guidance, not evidence that the hop was solved, and it receives no feasibility status unless the analyzer actually runs a separate scenario for it. Framework findings must identify the hop they apply to and cannot be projected across a missing hop.

The staged plan first handles direct Composer blockers, then applies the selected package changes, then follows covered framework hops in ascending order. It never recommends crossing a missing hop. Neither Composer success nor framework coverage upgrades the other dimension.

## Schema 0.7

Schema `0.7` adds top-level platform provenance and separates raw source inventory from actionable source impact:

- `platform` records analyzer PHP, current and target PHP values with their provenance, whether extension assumptions were explicit, whether their coverage is none, partial, or complete, the provenance of unmodeled values, and ordered present/absent/version assumptions when explicit. A partial set uses `mixed` provenance because unlisted extensions still come from the analyzer runtime;
- `source_inventory` preserves deterministic AST observations;
- `source_impact` contains only observations correlated with a changed package or applicable framework rule, with `affected_package`, ownership confidence, relevance, reason, severity, exact occurrences, and evidence;
- `transition.framework_guidance` holds framework support status and ordered hop coverage without changing `resolution.status`; framework findings carry `applies_to_hops` references so advice cannot silently cross a gap.

Platform determinism is scoped to explicitly modeled extensions. Equivalent presence, absence, or exact-version assumptions must produce the same normalized decision for that named extension on every supported host. A partial assumption list does not claim complete host independence: unlisted extensions continue to come from the analyzer runtime, remain labeled with `unmodeled_provenance: analyzer_runtime`, and can still affect Composer resolution. A future complete target-platform input is required before the report may claim that no extension result depends on host state.

Symbol ownership is derived without loading target code. The analyzer indexes root `autoload` and `autoload-dev` metadata plus locked-package `autoload` metadata. PSR-4 and PSR-0 longest-prefix matching applies only to class-like symbols; function and constant ownership requires a declaration of the same symbol kind from an available classmap or files entry, and constants retain PHP's case sensitivity. Duplicate best matches are `ambiguous`. Exact mapping inspection is inventory-scoped and bounded to 2,000 files; unsupported, unavailable, over-limit, dynamically generated, or dynamically registered mappings add uncertainty instead of inventing an owner. An unresolved owner remains `null` with `ownership: unknown`.

Package-correlated `source_impact` entries are emitted for removed, upgraded, downgraded, major-jump, and same-version source or distribution reference changes. Framework-correlated entries remain actionable independently, and use `package_change_and_framework_rule` when both correlations apply. Repeated uses of the same symbol and usage type form one finding whose occurrences retain every distinct file and line record. Risk and effort weight actionable severity, correlation, ownership uncertainty, and a bounded occurrence count. Inventory observations that match neither condition remain only in `source_inventory` and do not contribute to source-change planning, risk, or effort.

See [Schema and compatibility](schema.md) for the `0.6` migration. Schemas and canonical snapshots from `0.2` through `0.6` are checksum-locked by the v0.2 contract test and remain unchanged.

## Adapter and external-execution contract

v0.2 replaces the CLI's Laravel-specific class probe with installed-package discovery through `extra.php-upgrade-preflight.framework-adapters`. The value is a nonempty list of nonempty integration-class names. Discovered classes must be autoloadable, constructible without arguments, implement `FrameworkIntegration`, and return a nonempty name. Package discovery order and integration execution order are deterministic. Duplicate classes and duplicate case-insensitive names are errors; invalid advertised registrations fail closed. Packages absent from the running Composer installation and packages without adapter metadata contribute nothing. An explicitly requested but unavailable adapter remains invalid CLI input with exit code `2`. The full public contract is in [Framework adapters](adapters.md).

Laravel supplies the same integration through this metadata in standalone CLI mode. Its automatic detection and analyzer behavior remain unchanged, while its service provider continues to register the parity-tested Artisan entry point.

The only supported external execution path for v0.2 is an external Composer tools-directory installation. No PHAR or versioned container image is a v0.2 deliverable. Release package ZIPs remain Composer distribution artifacts with checksums and release provenance; repository container files remain development-only. The release gate analyzes the PHP 7.4 Laravel fixture from an external installation and verifies the target's recursive digest is unchanged.

## Representative-corpus budgets

The representative corpus is the six application-shaped Laravel fixtures. With a warm dependency install, one process, the deterministic fixture runner, and debug disabled, the limits are:

| Dimension | Budget |
| --- | ---: |
| JSON report | 128 KiB per fixture |
| Markdown report | 64 KiB per fixture |
| All 12 reports | 768 KiB combined |
| Six-fixture runtime | 30 seconds |
| Peak allocated memory | 256 MiB |
| Seeded secret leaks | 0 on every checked surface |
| Determinism | 3 normalized reruns must be byte-identical |

The zero-leak budget covers canonical JSON, Markdown, evidence, exception messages, debug output, console diagnostics, CI logs, and release archives. Default shareable reports use `[PROJECT_ROOT]`, `[REPORT_OUTPUT]`, `[LOCAL_REPOSITORY]`, and `[ANALYZER_WORKSPACE]` instead of absolute local roots. Source locations remain project-relative. Exact analyzer workspace paths require explicit debug mode; debug artifacts are non-shareable, and credential redaction remains mandatory in that mode.

Ordering is part of the budget contract: targets and package changes use package name; framework assessments and hops use framework/major order; inventory uses canonical file order and parser traversal order with exact file/symbol/type/line duplicates merged; actionable impact follows inventory order; framework findings follow integration registration and rule-catalog order. Scenario order, uncertainty order, and evidence order retain their documented production order. Enforcement is deterministic and does not perform network access.
