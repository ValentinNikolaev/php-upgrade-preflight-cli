# v0.3 staged-analysis contract

This document describes the published v0.3.x contract introduced in v0.3.0 and current in v0.3.2. The normative machine-readable form is [`tests/fixtures/contracts/v0.3.json`](../tests/fixtures/contracts/v0.3.json); schema consumers must use [`upgrade-report-v0.8.schema.json`](../packages/core/resources/schema/upgrade-report-v0.8.schema.json).

## Three independent conclusions

Schema 0.8 reports three conclusions that answer different questions:

- `resolution.status` describes only the direct final-target Composer scenarios.
- `transition.framework_guidance[].status` describes only adapter rule coverage.
- `staged_resolution.status` describes only the executed adjacent-stage Composer chain.

Each dimension can be `blocked` or unsupported while another is feasible or supported. Consumers must not use one to upgrade, suppress, or infer another.

## Stages and candidate state

One active optional `FrameworkStageTargetProvider` may supply a contiguous ordered plan. The required v0.2 adapter interfaces are unchanged. Every stage contains exact package targets, an exact PHP analysis value supported by request evidence and checked against adapter minimum metadata, its execution state, resolution status, attempts, selected attempt, package changes, blocker and source-impact references, source assessment, tests, risk, effort, recommended actions, and input/output fingerprints.

The analyzer starts with the original manifest and lock. Attempts run only in analyzer-owned temporary workspaces. When adapter-evidenced root remediations exist, they run in this order:

1. exact stage targets;
2. the first normalized adapter-evidenced root remediation;
3. all adapter-evidenced root remediations plus Composer's all-dependencies mode for eligible locked direct and transitive packages.

When no adapter-evidenced root remediation exists, the second and final attempt retries the exact stage targets with Composer's all-dependencies mode. Its strategy is `locked_package_remediation`.

A candidate is selectable only after a full-target Composer success and when no blocking registry entry remains active for that attempt. Its manifest, lock, effective platform, and execution policy form the next stage's input. The analyzed project is never changed.

The production Laravel provider accepts one rooted `laravel/framework` target and builds the assessed contiguous adjacent path from Laravel 7 through 13. A 7→9 request retains its direct guidance dimension but staged solving executes 7→8 then 8→9 because every reported feasible stage needs its own adjacent Composer evidence. Illuminate-component-only projects and mixed Laravel-family target sets remain staged guidance gaps.

Each stage prefers the request's exact final target PHP when it satisfies the adapter's documented PHP constraint. If no compatible final PHP was requested, the exact current PHP may be used. A minimum constraint is never converted into an invented exact value: when neither request value is safe, staged solving is skipped with `analysis_php_unavailable` evidence.

Every evaluated or downstream-skipped stage records its effective platform and Composer-policy digests, safe policy configuration, total duration, and evidence references. The full manifest, lock, platform, and execution-policy digests remain in the input and output state fingerprints. Those digests identify content rather than location: they read the sanitized manifest and lock, normalize the separators after an exposure marker, and exclude the Composer `content-hash` derived from the analyzer's own workspace manifest, so the same project analyzed on another host or from another directory produces the same chain.

## Blocker registry

`staged_resolution.blocker_registry` is always an ordered array. Every entry has stable identity, stage, first attempt and scenario, category, subject, blocking package, requested and blocking constraints, dependency path, confidence, evidence, first/last observation, lifecycle history, and current lifecycle.

The lifecycles are `detected`, `persists`, `resolved`, and `superseded`. A remediation may resolve no blockers, a subset, or several and may reveal a different blocker. Later success retains earlier records. Exact identity is deduplicated within an attempt and across attempts in one stage; entries from different stages never merge. Similar wording or package names do not merge distinct constraints, dependency paths, platforms, or stages.

## Stop and uncertainty rules

Stage execution state is `evaluated` or `skipped`, independent of its nullable per-stage resolution status. Evaluated resolution statuses are `feasible`, `feasible_with_changes`, `blocked`, and `unknown`. Missing or ambiguous targets, guidance gaps, unavailable exact stage PHP, provider conflicts, and hop-budget failures skip staged solving as unknown. Solver blockers stop as blocked. Timeouts and operational failures stop as unknown. All later planned stages are skipped with stage-specific evidence; the analyzer never invents results after a stop.

The maximum scenario count is the derived product of the independently enforced hop and per-stage attempt caps. It is reported as a budget invariant, not as a separate runtime stop condition.

Only the original source snapshot is inspected. Every stage states that boundary. Source usages are correlated independently with that stage's selected package changes and applicable framework rules, then de-duplicated in the staged source-impact registry with stable stage references. Later-stage findings are unresolved review evidence, not claims that an earlier source edit was applied.

Stage plans are derived only from executed outcomes. A feasible stage may recommend applying its selected candidate and running its stage-scoped tests. A blocked, unknown, or skipped stage recommends only remediation and a rerun; the plan ends there and never recommends a later unproved transition. Aggregate risk and effort count exact package transitions and source occurrences once and never use Composer scenario count as an application-change multiplier.

## Platform and execution boundary

The target-platform profile schema is `1.0`: `{"schema_version":"1.0","completeness":"partial|complete","packages":{...}}`. It accepts exact PHP, `ext-*`, `lib-*`, PHP-subtype, and Composer-platform values, or `false` for absence. Partial means unlisted platform packages may still come from the analyzer runtime. Complete is closed-world for supported safely simulated classes: unlisted values are modeled absent. Composer platform packages tied to the executable remain explicitly `toolchain_bound` rather than falsely simulated.

Precedence is request, profile, then original project `config.platform`. Equal request/profile values are accepted with request provenance, matching same-layer duplicates collapse deterministically, and contradictory values are rejected before Composer runs. Lower-priority project values are overridden. A complete profile cannot be combined with a presence-only extension assumption because completeness requires an exact value or absence.

`request_summary.target_platform_profile` records schema, completeness, canonical SHA-256 digest, and safe `php_api` or `file` provenance. `platform.profile` additionally records supported classes, closed-world status, sorted toolchain-bound package names, and sorted effective decisions with name, class, state, version, provenance, and simulation. Local profile paths never enter canonical output.

Complete profiles require Composer 2.2 or newer; an older Composer yields operationally unknown before workspace creation rather than silently weakening completeness. The complete-profile guarantee removes analyzer-host inheritance only for supported safely simulated platform-package classes. Repository metadata, network and credential state, downloads, and Composer executable differences remain outside that guarantee and are reported or controlled separately.

`composer_execution` records the detected version, expected range, compatible or restricted mode, scenario and diagnostic timeouts, repository-source mode, global configuration and credential inheritance, and every disabled side effect. Compatible mode retains host configuration for private repositories. Restricted mode uses empty analyzer-owned Composer configuration/authentication and cache state, scrubs controlled proxy and askpass environment sources, and requests Composer's best-effort offline behavior. A restricted metadata miss is operationally unknown, not a solver blocker. Restricted mode does not claim process or OS network isolation; the configured executable, helper subprocesses, embedded project credentials, system trust, and OS controls remain residual boundaries. The complete threat model is documented in [Composer execution policy](composer-execution.md).

Staged solving is bounded to six hops, three attempts per stage, eighteen scenarios, 128 Composer and diagnostic processes in the projected worst case, 300 seconds per scenario, 900 seconds per stage, 1,800 seconds aggregate, 256 MiB memory, 512 KiB canonical JSON, and 256 KiB Markdown. Scenario duration covers the complete analyzer-owned workspace lifecycle, including target diagnostics and cleanup. The effective staged scenario timeout is the lesser of the request timeout and 300 seconds, and the effective staged diagnostic timeout is likewise the lesser of the request diagnostic timeout and 300 seconds. An attempt starts only when that full scenario timeout fits inside both the remaining stage and aggregate budgets. Measured diagnostic and cleanup time counts toward both budgets and can prevent subsequent work; exhausting either budget stops the chain as operationally unknown. A provider plan whose target diagnostics could expand beyond the process cap is skipped as operationally unknown before Composer runs.

## Compatibility and scope

Schema 0.7 and the signed v0.2.1 artifacts remain immutable under [`tests/fixtures/contracts/v0.2.1`](../tests/fixtures/contracts/v0.2.1). See [Schema and compatibility](schema.md) for the 0.7→0.8 migration.

v0.3 does not add Symfony or CodeIgniter adapters, a PHAR, a supported runtime container, a higher PHP runtime floor, source modification, project Composer-file modification, application execution, or a runtime-compatibility guarantee.
